## 摘要

随着大语言模型与自主智能体成为代码的主要生产者，脚本语言的评价标准正在变化：**Token 成本、上下文窗口占用、生成代码的可预测性、以及宿主侧的失控防御**，其权重开始超过"人类手写的表达便利性"。而 Python / JavaScript / Lua 的设计年代均未把这些约束纳入考量。

**Ada-D** 是用 Rust 实现的现代脚本语言，以三条命题为设计公理：

1. **Token 密度第一**：语法层面剔除一切可推导的样板（分号、`return`、类型声明、冗余括号）。
2. **低困惑度**：只采用 LLM 高频见过的语法形态（Rust / TypeScript / Python 的交集），不发明冷门符号。
3. **双模式一体**：既是可独立运行的 CLI 语言，也是可极轻量嵌入 Rust 宿主、具备资源熔断能力的沙箱引擎。

## 1. 背景：AI 时代的语言困境

| 困境 | 传统方案的问题 | Ada-D 的应对方向 |
| :--- | :--- | :--- |
| **Token 成本与上下文膨胀** | 格式样板（强制分号、冗长关键字、闭包样板、深层括号）在 Agent 多轮调用中放大为可观的 API 成本与延迟 | 语法级压缩：无分号、`fn`/`let`/`mut` 短关键字、单行函数、隐式返回、管道算子 |
| **AI 代码的不确定性** | Python/Node 运行时偏重，难以做指令级计费与轻量隔离 | 指令燃料（Fuel）熔断 + 权限分级 + 资源预算（部分已实现，部分规划中） |
| **Rust 生态嵌入式脚本的空缺** | Lua 绑定有心智与安全负担；Rhai 无 JIT；Wasm 隔离好但跨边界互操作成本高 | 纯 Rust 实现、寄存器 VM、面向宿主的声明式嵌入 API，保留 JIT 演进路径 |
| **结构性数据交互样板** | JSON 与语言字面量之间需要序列化代码 | `{}` / `[]` 字面量与 JSON 同构，`json` 模块零拷贝互转 |

## 2. 设计哲学

| 原则 | 含义 | 在语法/运行时中的体现 |
| :--- | :--- | :--- |
| Token-Density First | 在保持可读性的前提下最大化每 Token 的语义密度 | 无强制分号、单行函数、隐式返回、`mut` 一行声明 |
| Low Perplexity for LLMs | 大模型零示例即可生成正确代码 | 只用 Rust/TS/Python 的交集形态；`?.`、`??`、`|>`、`match` 均为高频已知符号 |
| Dual Execution Modes | 独立 CLI 与嵌入式引擎同一套实现 | `ada_cli` 与 `ada_engine` 共享同一 VM；`Engine` 提供 `register_fn` / `eval<T>` |
| Tiered Performance | 冷启动毫秒级解释，热点再提升 | Tier 0 寄存器 VM 已落地；Tier 1 VM 优化与 Tier 2 Cranelift JIT 为规划项 |
| Fail-Safe Sandboxing | 宿主永远不该被脚本拖死或击穿 | Fuel 熔断已落地；内存预算、墙钟超时、权限分级为规划项（详见开发计划 M5） |

## 3. Token 密度论据

### 3.1 语法级优化清单

| 语言特性 | 传统做法 | Ada-D 方案 | 节省来源 |
| :--- | :--- | :--- | :--- |
| 行终止符 | 强制末尾 `;` | 换行自闭合（ASI） | 每行 1 个 Token |
| 函数声明 | `function name()` | `fn name()` | 关键字更短 |
| 简单求值 | `{ return a + b; }` | `= a + b` | 省去 `{` `return` `;` `}` |
| 返回值 | 强制 `return expr` | 末尾表达式隐式返回 | 消除高频 `return` |
| 异步链式 | `(await fetch()).json()` | `fetch().await.json()` | 消除外层括号层级 |
| 多层嵌套转换 | `f(g(h(x)))` | `x \|> h() \|> g() \|> f()` | 消除右侧闭合括号 |
| 空值防御 | 多层 `if (x != null)` | `x?.a?.b ?? default` | 消除分支样板 |
| 字符串拼接 | `format(...)` / 模板串 | `$"User {name}"` | 消除函数调用样板 |
| 条件赋值 | `cond ? a : b` | `if cond { a } else { b }` | 复用已有结构，不引入新符号 |

### 3.2 同逻辑代码的形态对比（示意，非基准）

| 逻辑需求 | Python | JavaScript / TypeScript | Ada-D |
| :--- | :--- | :--- | :--- |
| 过滤 + 映射 + 求和 | `sum([x*2 for x in arr if x>0])` | `arr.filter(x=>x>0).map(x=>x*2).reduce((a,b)=>a+b,0);` | `arr \|> filter(x => x > 0) \|> map(x => x * 2) \|> sum()` |
| 带分支的纯函数 | 8~12 行 | 10~15 行 | 4~6 行 |

> ⚠️ **数据状态：待验证**。上表的 Token 降幅与行数差异是**设计预期**，尚未在任何分词器（cl100k_base / o200k_base / Llama3）上实测，也未经基准套件验证。相关验证任务：开发计划 T6.1（基准）与 T7.4（AI Prompt 规格单页）。
> 另注：第二行示例依赖迭代器适配器与闭包捕获，二者当前**尚未实现**（见 [DEVELOPMENT_PLAN](DEVELOPMENT_PLAN.md) 的 T2.1 / T2.2）。

### 3.3 反例约束（不为省 Token 而牺牲的东西）

- 不引入晦涩符号（如自定义运算符、隐式类型魔法）。
- 不用"位置敏感"的语法（除已有的换行 ASI 与续写算子白名单）。
- 不为压缩 Token 牺牲错误可定位性（所有错误须带 `file:line:col`，见运行规范 §8）。

## 4. 与既有方案的差异化

| 维度 | Lua | Rhai | Wasm | **Ada-D（目标）** |
| :--- | :--- | :--- | :--- | :--- |
| 实现语言 | C | Rust | 多语言 | **Rust** |
| 嵌入式绑定成本 | 需 C FFI 与栈管理 | 低 | 高（需序列化/ABI 设计） | **低**（`Engine` + `register_fn`） |
| 数据字面量 ↔ JSON | 需库 | 需库 | 需序列化 | **同构**（`{}`/`[]` + `json` 模块） |
| 资源熔断 | 无 | 部分（操作数限制） | Fuel 计量 | **Fuel 已落地**，内存/超时规划中 |
| 异步 | 协程（宿主驱动） | 无 | 依赖宿主 | 语法已具备，运行时规划中 |
| JIT | LuaJIT（独立实现） | 无 | 依赖引擎 | Cranelift（规划中） |
| AI 语法定向优化 | 无 | 无 | 无 | **核心设计目标** |

## 5. 目标场景

1. **AI Agent 工具执行器**：LLM 生成短脚本做数据清洗、结构化转换、条件路由；宿主需要"绝不挂死、绝不越权"的执行环境。
2. **Rust 应用的规则/配置层**：把易变的业务规则外置为脚本，宿主注册领域函数（`register_fn`）。
3. **数据处理管道**：`json.parse` → 管道变换 → `json.stringify`，替代一次性胶水代码。
4. **教学与实验**：语法小、实现完整、可 dump 字节码，适合编译原理教学与语言实验。

**非目标**：通用大型应用开发语言、系统编程、需要强类型保证的大型工程（见开发计划 §9）。

| 闭包 upvalue 捕获 | ✅ M2 已完成：引用共享（可写捕获）、多级传递、每轮循环变量独立槽 |

| **宿主崩溃防护（脚本 panic 逃逸）** | ✅ M1 已修复 5 类可触发 panic 的脚本输入（`%0`、整数溢出、移位越界、UTF-8 索引、`min([])`），并有 17 个回归用例（见 [SPEC_RUNTIME §6](SPEC_RUNTIME.md)） |
| 宿主嵌入 API（`Engine` / `register_fn` / `eval<T>`） | ✅ 可用（公共类型已 re-export；权限分级与资源预算仍缺） |

| 统一迭代器协议 | ✅ `for..in` 已统一，`map`/`filter`/`take`/`skip`/`collect`/`count`/`find`/`any`/`all`/`enumerate`/`rev`/`join`/`sum` 与方法链均可用；⚠️ 当前为即时求值（非惰性链，见决策 D3） |

## 7. 结论

Ada-D 的赌注是：当代码的主要作者变成模型时，**语法的 Token 效率与运行时的失控防御**会成为语言设计的一等约束。本白皮书定义了这一约束下的目标形态；[开发计划](DEVELOPMENT_PLAN.md) 定义了从当前 `0.1.0` 走到该形态的可验收路径；各 [SPEC](README.md) 文档定义每一步的规范边界。
